# ADR-009：COBRApy 只作外部 GEM 的入口与 QA，不作 pcSec 默认后端

状态：accepted（追认 2026-07 已在架构中生效的边界）  
日期：2026-07-31（决策发生于 2026-07-02，本文为补记）  
关联：不替代任何既有 ADR。边界本身已写在 [架构](../architecture.md)「已有能力」，本文补的是**为什么**。

## 背景

当时讨论过一件很自然的事：项目自己维护了一套模型构建与 LP 组装代码，而 COBRApy 是代谢建模领域的事实标准库，功能更全、社区更大。「整体换成 COBRApy 作主后端」是一个真实的候选方案，做过逐维度对照。

结果是**否掉**。架构文档记录了结论（「不作为 full pcSec 默认后端」），但没记理由——于是这条边界看起来像是历史惯性，而不是判断。

## 决策

**COBRApy 的角色限定为三件事**：外部 GEM 导入、基础 QA、小模型语义验证。pcSec 主路径的模型构建与求解不走它。

### 为什么不换

1. **pcSec 的约束不是通用 GEM 语义。** 分泌路径的酶容量耦合、蛋白质量守恒、错误折叠稀释、核糖体与蛋白酶体负担这些约束块，是这个模型体系特有的构造。用通用库表达要么绕，要么得在库外再搭一层——那就没省下什么。
2. **既有对照资产会作废。** 与旧 MATLAB 实现的逐行 LP 比对（见 [ADR-008](008-matlab-comparison-claim-boundary.md)）依赖对约束行的完全掌控。换后端等于把已经建立的比对基础全部推倒重来，而收益只是「用了标准库」。
3. **换后端不解决任何在手问题。** 当时（以及现在）真正卡住项目的是数据缺口——绝对容量、改造→产量可链数据集。换库一条都不解决。

### 保留 COBRApy 的理由

外部 GEM 的解析、格式兼容和基础一致性检查是通用问题，自己写没有价值。这一档正是标准库最该被用的地方。

## 不变量

- 默认求解路径不经 COBRApy。
- 换默认 solver / 后端属**明确不做**（已在 handoff 硬约束中）。
- COBRApy 路径产出的结论不得直接作为 pcSec 主路径结果呈现。

## 后果

- 正面：「为什么不用那个标准库」这个必然会被问到的问题有了出处；边界不再像历史惯性。
- 代价：外部 GEM 生态里的新功能不会自动流进主路径。这是接受的——主路径要的是对约束的完全掌控，不是功能广度。
- 风险边界：本 ADR 不禁止在 QA / 验证一侧继续用 COBRApy，也不排除将来因**具体**理由重新评估——但那需要一条取代本 ADR 的新 ADR，而不是顺手改后端。
